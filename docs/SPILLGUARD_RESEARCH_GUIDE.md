# SpillGuard Repro: local research guide

Prepared on 16 October 2026. The original [decision dossier](research/2026-10-16-spillguard-opportunity/research-dossier.md) remains the scope reference. See the [execution ledger](SPILLGUARD_EXECUTION.md) for completion evidence and open gates.

The implementation extends the existing Windows collector, analyzer, CUDA helper and AetherOS replay view. It is an experiment harness and evidence viewer. It does not reserve VRAM, control the WDDM scheduler or establish a residency cause from shared-memory counters.

## Entry points

Run from the repository root with the existing Python environment. All examples create new output directories; never reuse an evidence directory. In this Codex workspace, prefix shell commands with `rtk proxy` as instructed by RTK.md.

```powershell
agent/.venv/Scripts/python.exe bench/repro.py validate bench/recipes/overhead-cuda.json
agent/.venv/Scripts/python.exe bench/repro.py preflight --recipe bench/recipes/overhead-cuda.json
agent/.venv/Scripts/python.exe bench/repro.py run --recipe bench/recipes/overhead-cuda.json --out traces/repro/my-new-cuda-run
agent/.venv/Scripts/python.exe bench/repro.py verify traces/repro/my-new-cuda-run
agent/.venv/Scripts/python.exe bench/research.py --help
```

Native PDH counters and CUDA require Windows/NVIDIA access; an unavailable or denied counter is not a zero measurement. Live Repro currently accepts one NVIDIA adapter whose CUDA name matches the selected DXGI adapter. AMD, Intel, multiple NVIDIA adapters and remote/device-independent operation have not been validated. The original observer can still degrade gracefully outside this lab path.

## Recipes, preparation and timing

Actions declare bytes, phase, offset, duration, repeated-touch interval, and hold/compute mode. Supported anchors are pressure start, client request start and first streamed output. These are observable boundaries; an exact internal model-load or prefill boundary is unavailable. CUDA probes use pressure-start anchoring. Ollama cold preparation starts a private server with an empty loaded-model list; warm preparation runs a warmup request; idle/resume adds a declared idle interval. Cold means a fresh private runtime, not a flushed OS file cache or powered-off GPU.

Hold, ramp, burst and release/reacquire schedules are generated by the campaign module. Pressure is credited only when enough valid samples overlap target execution and each requested action is observed. Short tasks may not cover every action: those manipulations are inconclusive. Requested compute duty is a bounded scheduling input, not a promise of exact GPU utilization. The small arithmetic control also consumes power and changes clocks.

The target's model/prompt digests, context, precision-containing model identity, output requirement, seed and options stay fixed during reduction and remedy comparison. The installed Qwen3-VL text-input recipe uses a multimodal architecture without images. It is not a second purely text architecture. No image-generation or D3D12 graphics helper is included.

Matched blocks retain baseline, pressure and recovery. The campaign randomizes baseline/pressure order and leaves recovery last; each stage uses a fresh target instance. A fixed-order pilot remains labeled fixed-order. Reset is checked through application completion and recovery ratio; no persistent application-wide reset guarantee is implied.

The primary Ollama metric is server-reported decode milliseconds per generated token. Total completion and first streamed-output times are separately recorded. Server token durations do not provide a distribution of individual token latencies. CUDA uses completion milliseconds for fixed write work.

## Decisions and reduction

`FAIL` means a completed slowdown witness at the declared threshold with fixed work, measured manipulation and recovery. `PASS` means a valid non-reproduction. `INCONCLUSIVE` includes invalid telemetry, work/output changes, CPU offload, incomplete execution, missing overlap, host pressure or failed reset. These labels are about the operational predicate, not a proven paging mechanism.

```powershell
agent/.venv/Scripts/python.exe bench/research.py search --recipe <recipe.json> --method phase-aware --max-tests 30 --max-executions 30 --max-looks 1 --out traces/repro/new-search
agent/.venv/Scripts/python.exe bench/research.py fixture-comparison --out traces/repro/new-fixture-comparison
```

Methods are greedy, ddmin, ProbDD-style, no-reduction, tiny exhaustive and phase-aware. Tiny exhaustive is limited to ten actions and deletion subsets; it does not exhaust all byte/time values. The ProbDD-style comparator follows expected-gain selection and probability updates inspired by the [primary paper](https://xiongyingfei.github.io/papers/FSE21a.pdf); it is not a replication of its full implementation or proof.

Phase-aware reduction can delete actions, halve held bytes, shorten duration and narrow phase overlap. It preserves a classified PDH counter/phase proxy within declared tolerances. It does not directly preserve an unobserved residency mechanism. Missing cold-start signatures can prevent evaluation. Original and final witnesses are tested separately. Only checked single-neighbor non-reproductions plus fresh final reproduction support a local 1-minimal certificate; budget exhaustion, ambiguity and a different signature prevent that claim. No global minimum is claimed.

The fixed-size default uses strict concordance across the requested matched blocks. Optional bounded looks use exact binomial intervals with a predeclared Bonferroni correction across looks, conditional on independent stationary whole-block outcomes. Ambiguous/invalid outcomes do not become passes or update ProbDD dependency probabilities. The physical-execution budget reserves room for fresh validation. Repeated within-session blocks do not by themselves establish independence across days, drivers or machines.

## Interventions and remedies

```powershell
agent/.venv/Scripts/python.exe bench/research.py background --recipe bench/recipes/arithmetic-control-smoke.json --out traces/repro/new-control
agent/.venv/Scripts/python.exe bench/research.py remedy --recipe <failing-recipe.json> --out traces/repro/new-remedy
```

The remedy workflow first requires a fresh original failure. It compares pressure-off, half owned allocation and serialization of owned background work after the full matched block. Serialization actually executes that background schedule and records its completion, added delay and wall time. Its delay includes experimental controls/setup; it is not an interactive user-latency estimate. Invalid variant or background execution makes the comparison inconclusive. Targets are unchanged. This is a fresh-instance comparison, not a persistent-process live unload or arbitrary application coordination. There is no verified smallest acceptable remedy in the current empirical evidence.

Only original owned process handles or a private Windows job authorize termination. The normal Ollama server, other applications, model files and driver settings are not modified. Cancellation and timeout paths close owned helpers; partial runs and failures remain evidence. Host guards enforce the recipe's available-RAM floor and 90% commit limit. Do not lower guards to turn a host-memory failure into an apparent GPU witness.

## Campaign and analysis

The saved plan `bench/plans/20261016/campaign.json` contains 72 cells and 432 planned whole matched blocks. Its three pressure levels are provisional engineering values, not calibrated severe-failure levels. `gate.json` is false and the final campaign has executed zero cells.

Execution requires a gate bound to the immutable plan hash, integrity-verified live failure/reset evidence for every target/preparation and valid calibration at every planned level. A software fixture, an unrelated workload or an unchecked boolean cannot authorize execution. Checkpoints reject changed plans and ambiguous interrupted-cell reuse. Resource-guard failures stop the campaign. Fresh sessions and thermal/power controls still require a declared experimental procedure; randomized within-process ordering is not a replacement for them.

```powershell
agent/.venv/Scripts/python.exe bench/research.py campaign --plan bench/plans/20261016/campaign.json --gate bench/plans/20261016/gate.json --out traces/repro/new-final-campaign
agent/.venv/Scripts/python.exe bench/research.py analyze --bundles <bundle-a> <bundle-b> --out artifacts/new-analysis
agent/.venv/Scripts/python.exe bench/research.py overhead --recipe bench/recipes/overhead-cuda.json --pairs 3 --seed 42 --out traces/repro/new-overhead
```

The campaign command currently refuses this plan. Analysis verifies bundle hashes, rejects duplicate directory inputs, separates recipe/purpose/origin, includes invalid/missing planned blocks in denominators, and reports whole-block summaries. Search observations never become fresh validation. Exact binomial intervals carry independence/stationarity assumptions; no per-token pseudoreplication or p95/p99 application claim is made. A three-pair overhead check is preliminary, not a universal efficiency result.

## Inspect and replicate

Open SpillGuard in AetherOS. In its evidence desk, select raw `report.json`, a new or earlier `reduction.json`, or analysis `summary.json`. Stage JSONL files use the existing replay path. Imports remain in browser memory and survive window restore/maximize; Clear imported report removes the displayed report. There is no experiment-launch HTTP endpoint. The UI shows reported claims and does not independently verify local manifests.

```powershell
agent/.venv/Scripts/python.exe bench/research.py export --bundle <verified-bundle> --out artifacts/new-review-package
agent/.venv/Scripts/python.exe bench/research.py verify-export artifacts/new-review-package
```

Exports are local only. An allowlist omits raw logs/events, original process names/PIDs/start times, hostnames and path-bearing machine metadata; replay timestamps become relative and process labels become pseudonyms. Prompts are redacted by default. Code and dependencies can still require review; this is not a formal privacy guarantee or a release-license audit. Model weights and runtime binaries are excluded. Hashes establish integrity against an accidental edit, not authenticity against an adversary who can rewrite both content and manifest.

The release package is `artifacts/spillguard-repro/20261017-release-replication/`: measured results, sanitized stage replays, 35 source/dependency files and a manifest. From its `source/agent` directory, use a compatible Python environment to run `python -B -m spillguard repro validate ../../recipe-template.json`, then `python -B -m spillguard repro run --recipe ../../recipe-template.json --out <new-absolute-directory>`. `-B` avoids adding unlisted bytecode caches to the sealed export. The source snapshot records the implementation at that measured run, rather than automatically following later repository edits; it is not a hermetic runtime, CUDA-driver lock or independent replication.

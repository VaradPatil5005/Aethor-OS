1. The big picture

1.1 What was built

The project has three connected parts:

  1. AetherOS (written "Aethor OS" on the boot screen) — a retro-style desktop operating system that runs entirely inside a web browser. Behind its windows is a small simulated microkernel written in TypeScript. It creates processes, schedules them on two simulated CPU cores, gives them memory pages, detects deadlocks, keeps a journaled file system and records kernel events. Every textbook concept is visible and interactive: you can change the scheduling algorithm, change the page-replacement policy, inject a deadlock, cut the power to the disk and run recovery.
  2. SpillGuard — a real monitoring agent written in Python that runs on Windows. Once per second it reads the operating system's own GPU memory counters for every process and detects the moment a program's data stops fitting in the graphics card's memory (VRAM) and starts being placed in ordinary system RAM. This is called a spill. The agent serves AetherOS to the browser and streams its measurements into the SpillGuard app, so the simulated OS and the real hardware are shown side by side.
  3. SpillGuard Repro — a research tool built on the agent. It runs controlled, repeatable experiments: a local AI language model (Qwen2.5-3B in Ollama) is timed alone, then with a second "co-tenant" process occupying GPU memory, then alone again. It saves every measurement in a tamper-evident bundle, classifies each trial as FAIL / PASS / INCONCLUSIVE with strict rules, and tests which fixes remove the slowdown.

1.2 Why these two belong together

An OS course teaches virtual memory: when the fast memory (RAM) is full, the OS moves some pages to slower storage (disk), and if this happens too often the system thrashes. Exactly the same thing happens one level up. A GPU has its own fast memory (VRAM). When programs together need more VRAM than exists, Windows' video memory manager moves some GPU data to slower system RAM, reached over the PCIe bus. Nothing crashes — the program just runs much slower, silently. AetherOS teaches the concept with a simulation; SpillGuard measures the real thing on real hardware; the research measures how much it costs and what fixes it.

3. AetherOS architecture

3.1 Layers

3.2 The kernel clock: a "tick"

Time in the simulated kernel is measured in ticks. A JavaScript timer calls Kernel.step() every 800 ms by default (speed is adjustable). One tick = one unit of CPU time. In each tick the kernel:

  1. puts whatever ran last tick back to READY, so every tick is a fresh dispatch decision (the policy decides whether the same process continues);
  2. synchronizes the per-core run queues with the list of ready processes;
  3. does work stealing if one core's queue is empty and the other has more than one process;
  4. under MLFQ, every 40 ticks applies aging (priority boost);
  5. asks the scheduler to choose one process for Core 0 and a different one for Core 1;
  6. counts a context switch whenever a core runs a different process than last tick, and emits an eBPF SCHED_SWITCH event;
  7. runs each chosen process for one tick (remaining burst −1), touches its memory frames (for LRU/CLOCK), records the Gantt chart entry;
  8. marks finished processes TERMINATED, records completion/turnaround time and frees their frames;
  9. adds one waiting tick to every process that was READY but not chosen; updates core load percentages.

Because the kernel uses no randomness, the same actions always produce the same result — it is deterministic, which makes it testable.

4.3 The six scheduling algorithms

A scheduler decides which READY process runs next. Preemptive means the OS can take the CPU away from a running process; non-preemptive means it runs until it finishes or blocks. Because AetherOS re-decides every tick, the shortest-job and priority policies behave preemptively.

Worked example: Round Robin

Two processes A and B, each needing 4 ticks, quantum 2, one core: the schedule is A A B B A A B B. A runs 2 ticks (its quantum), is rotated to the tail, B runs 2 ticks, and so on. (The project's built-in test checks exactly this pattern.) With quantum 4 the same pair would run A A A A B B B B, which is FCFS — a large quantum turns RR into FCFS.

4.4 MLFQ in detail

Aging is the cure for starvation: a process that waits a long time has its priority raised. In AetherOS, applyAging() moves every ready process back to Q0 every 40 ticks and resets its used quantum.

4.5 Dual-core SMP, affinity and work stealing

  • SMP (Symmetric Multi-Processing): several identical CPU cores share one memory and one OS. AetherOS simulates two cores, CPU_0 and CPU_1, and steps both every tick; the same process can never run on both cores at once.
  • Run queue: each core has its own queue of ready PIDs. A new process with affinity ANY is placed on the core with the shorter queue (load balancing).
  • Core affinity: a process can be pinned to core 0 or 1 (like taskset on Linux).
  • Work stealing: if a core's queue is empty and the other has N > 1 processes, the idle core takes ⌊N/2⌋ processes from the tail of the other queue (only those whose affinity allows it). This is how Linux's and many runtime schedulers keep cores busy.
  • Gantt chart: the two coloured timelines in Task Manager show which PID ran on each core in each of the last 30 ticks; grey = IDLE.

5. Memory management

5.1 Paging

Definitions

Paging divides a process's memory (its virtual address space) into fixed-size pages and physical RAM into same-size frames. A page table maps each page to a frame, so a process's memory need not be contiguous and there is no external fragmentation. Virtual memory lets pages that are not needed now live outside RAM.

AetherOS has 32 physical frames of 4 KB (a 128 KB toy RAM). A process of S KB needs ⌈S / 4⌉ pages. The Memory Map app draws the 32 frames as a coloured grid ("frame bitmap"); colour = owning process. Clicking a frame shows its PID, virtual page number, load time and last access time.

5.2 Page faults

A page fault happens when a page is needed but not in a frame. If free frames exist, the page is loaded; if not, a victim frame must be chosen and evicted — this is page replacement. In AetherOS, when a new process needs more frames than are free, each missing frame counts as one page fault and the replacement policy chooses victims (never frames of the same process). Every access to a process's frames (each tick it runs) updates lastAccessTick and sets the reference bit.

5.4 Protection rings and the General Protection Fault

CPUs have privilege levels called rings. Ring 0 = kernel mode (full access); Ring 3 = user mode (restricted). This is dual-mode operation: user programs cannot touch kernel memory. AetherOS's toy address space is 64 KB: 0x0000–0x3FFF (16 KB) is kernel space, 0x4000–0xFFFF is user space.

The "trigger GPF" action makes a Ring-3 process read address 0x0020 (inside kernel space). The memory manager's verifyAddressAccess traps it as a General Protection Fault (#GP), moves the process to WAITING (SIGSEGV_FAULT_HANDLER) and shows a register dump:

6. Deadlock

6.1 Definition and the four Coffman conditions

A deadlock is a set of processes each waiting for a resource held by another process in the set, so none can proceed. It can occur only if all four conditions hold at once:

  1. Mutual exclusion — a resource can be held by only one process (e.g. a mutex).
  2. Hold and wait — a process holds one resource while waiting for another.
  3. No preemption — resources cannot be forcibly taken away.
  4. Circular wait — a cycle P1 → P2 → … → P1 of "waits for".

Strategies: prevention (break a condition), avoidance (Banker's algorithm), detection and recovery (find the cycle, then kill or preempt).

6.2 Detection with a wait-for graph

AetherOS's resources: MUTEX_GPU, MUTEX_DISK, MUTEX_NET (1 instance each) and SEMAPHORE_IO (2). "Inject Deadlock" creates Worker_Thread_Alpha (holds MUTEX_GPU, waits for MUTEX_DISK) and Worker_Thread_Beta (holds MUTEX_DISK, waits for MUTEX_GPU).

DeadlockEngine.evaluateDeadlock builds an allocation matrix (who holds what) and a request matrix (who waits for what), then a wait-for graph: an edge P → Q means "P waits for a resource Q holds". It runs a depth-first search (DFS) keeping a recursion stack; meeting a node already on the stack means a back edge, i.e. a cycle. The PIDs on the cycle are reported. Complexity is O(V + E).

Mutex = mutual-exclusion lock (one holder). Semaphore = counter allowing up to N holders. For single-instance resources a cycle in the wait-for graph is necessary and sufficient for deadlock; with multiple instances a cycle is necessary but not sufficient.

6.3 Recovery

The Deadlock Lab offers "Preempt offending cycle processes": terminating a process on the cycle releases its locks and breaks the circular wait.

6.4 Banker's algorithm (deadlock avoidance)

Dijkstra's Banker's algorithm grants a request only if the system stays in a safe state — a state with at least one order (safe sequence) in which every process can obtain its maximum claim and finish.

  • Available[j]: free instances of resource j. Max[i][j]: the most process i will ever need. Allocation[i][j]: what i holds now.
  • Need = Max − Allocation.
  • Safety algorithm: Work = Available. Repeatedly find an unfinished process with Need ≤ Work; pretend it finishes and returns its allocation (Work += Allocation[i]). If all finish, the state is safe.

7. File system and crash consistency

7.1 Inodes and the superblock

An inode (index node) stores a file's metadata: number, name, type (file/directory), size, permissions (rw-r--r--) and parent.   • Power cut (triggerPowerCut): marks the superblock dirty, unmounts the disk and leaves a torn WRITE to /user/dirty_buffer.tmp in state PENDING. While unmounted, file operations fail.
  • fsck (file-system check, recoverFSCK): scans the journal; rolls back every PENDING (never committed) entry and replays every COMMITTED but not checkpointed entry; then marks the superblock clean and remounts.

This is the same idea as ext4's journal, NTFS's log file and database write-ahead logs: committed work survives a crash, uncommitted work disappears atomically.

eBPF (extended Berkeley Packet Filter) is a real Linux technology: small verified programs attached to kernel hooks (tracepoints) run when an event happens and store counts in BPF maps (key–value tables), or stream events through a ring buffer. 9. GPU memory fundamentals

9.1 GPU vs CPU

A CPU has a few powerful cores optimized for sequential, branchy code. A GPU (Graphics Processing Unit) has thousands of small cores that run the same operation on many data items at once (SIMD/SIMT parallelism). That is ideal for graphics and for the matrix multiplications inside AI models. A GPU computes fast only if it can be fed data fast — so its memory bandwidth matters most.

9.2 What is VRAM?

Definition

VRAM (Video RAM) is the GPU's own dedicated memory, physically on the graphics card (or next to the GPU chip on a laptop board). On this laptop it is 6 GB of GDDR6 (Windows reports 6002 MB as DedicatedVideoMemory). GDDR6 = Graphics Double Data Rate 6, memory designed for very high bandwidth.

Bandwidth = how many bytes per second can be moved. Measured on this GPU (experiment E1): writing to data in VRAM ran at 163.3 GB/s; writing to GPU data that the driver had placed in system RAM ran at 13.2 GB/s — 12.4 times slower.

Units: 1 MB = 106 bytes; 1 MiB (mebibyte) = 220 = 1,048,576 bytes; 1 GiB = 230 bytes. The research uses MiB; Windows counters report whole MB/MiB.

9.3 PCIe — the road between GPU and system RAM

PCIe (PCI Express) is the serial bus connecting the GPU to the CPU and system RAM. The GPU can read system RAM across it, but far more slowly than its own VRAM. That slow road is why spilling costs so much.

9.4 "Shared GPU memory"

Windows lets a GPU use part of system RAM as a second memory tier. Task Manager shows it as Shared GPU memory. Its limit is half of system RAM (Microsoft's documented rule): 7827 MB on this 16 GB laptop. Data in this tier is in normal DDR5 RAM and the GPU reaches it over PCIe.

9.5 WDDM and VidMm — the "operating system" of GPU memory

  • WDDM (Windows Display Driver Model): the architecture for graphics drivers on Windows. GPU memory is managed by Windows, not only by the vendor driver.
  • VidMm (Video Memory Manager): the part of the Windows graphics kernel (dxgkrnl.sys) that decides where every GPU allocation lives. It gives GPUs virtual memory: allocations get GPU virtual addresses, and VidMm can make them resident in VRAM or move (evict / demote) them to system memory when VRAM is over-committed — exactly like an OS paging RAM to disk.
  • Residency: whether an allocation is currently in VRAM (fast) or not.
  • Budget: the amount of VRAM Windows suggests one process should use, queried with DXGI's QueryVideoMemoryInfo. It is per calling process. On this laptop the budget was 5234 MB, yet under pressure the driver filled physical VRAM to 5954 of 6002 MB — so SpillGuard measures pressure against physical VRAM, not the budget.
  • DXGI (DirectX Graphics Infrastructure): the Windows API that lists graphics adapters and reports their memory.
  • LUID (Locally Unique Identifier): the ID Windows gives each adapter; counter names contain it, e.g. pid_32220_luid_0x00000000_0x00018056_phys_0.

9.6 NVIDIA "sysmem fallback"

Since driver version 536.40, when a CUDA program asks for more VRAM than is free, the NVIDIA driver on Windows does not fail with "out of memory"; it falls back to system memory (setting "CUDA – Sysmem Fallback Policy" in the NVIDIA Control Panel). The program keeps running, but slower. Project finding: cuMemGetInfo (CUDA's "how much memory is free?" call) reported 0 MB free from 5376 MB onward, and allocations kept succeeding — CUDA itself gives no signal that it is spilling. That is why an external detector is needed.

9.7 So what exactly is a "spill"?

Definition used in this project

A spill is when part of a process's GPU data that would normally live in VRAM is placed in system memory ("shared GPU memory") because VRAM is full. It shows up as the process's Shared Usage counter growing while the adapter's dedicated VRAM is near its physical limit. The program does not crash; memory accesses to the spilled part go across PCIe and the program slows down.

10. Local AI models — why they spill

The research target is a large language model (LLM) running locally. Key terms:

  • Parameters / weights: the numbers learned in training. Qwen2.5-3B has about 3 billion.
  • Quantization: storing weights with fewer bits (e.g. 4-bit instead of 16-bit) to save memory, with small accuracy loss. Formats: f16 (2 bytes), q8_0 (≈1.06 bytes), q4_0 (≈0.56 bytes) per value.
  • GGUF: the model file format of llama.cpp / Ollama; its header lists every tensor with its size and type, which SpillGuard reads to estimate memory.
  • Layers: a transformer is a stack of identical blocks (36 for Qwen2.5-3B). Offloading = putting layers on the GPU; num_gpu / -ngl chooses how many. If not all fit, the framework splits the model between GPU and CPU ("partial offload", called type A in SpillGuard).
  • Token: a piece of a word; the model generates one token at a time.
  • Prefill (prompt processing) reads the whole prompt in parallel; decode generates output tokens one by one. Decode reads all weights for every token, so it is limited by memory bandwidth — and therefore very sensitive to spill. The research metric is decode milliseconds per token (lower = faster).
  • Context length (num_ctx): how many tokens the model can attend to. The research uses 2048.
  • KV cache: memory that stores the attention keys and values of past tokens so they are not recomputed. Size grows with context.
  • Temperature 0 and seed 0: deterministic decoding, so the output text must be identical in every run — the research checks this with a hash.
  • Ollama: a local model server; its worker is llama-server.exe. llama.cpp: the C++ inference engine underneath.

KV-cache formula (used in SpillGuard's fit estimator)

KV bytes = 2 (keys and values) × layers × n_ctx × n_head_kv × head_dim × bytes_per_element
Qwen2.5-3B, ctx 2048, f16:  2 × 36 × 2048 × 2 × 128 × 2 bytes = 75,497,472 bytes ≈ 72 MiB

Measured total GPU footprint of the target in the research setup (weights + KV + CUDA context + work buffers): about 2421 MiB.

11.3 The spill detector (type B) — exact algorithm

Run once per second for every process, with hysteresis (different thresholds for entering and leaving a state, so it does not flicker):

ParameterDefaultMeaning
θhi (theta high)0.92Adapter "under pressure" when dedicated VRAM ≥ 92 % of physical VRAM.
θlo (theta low)0.85Pressure ends below 85 %.
Δ (delta)128 MBShared-usage growth above the process's own baseline that counts as spill.
k2Consecutive positive samples needed to enter SPILLING.
exit_k3Consecutive clear samples needed to leave SPILLING.
  1. Baseline: for each process, the minimum shared usage seen while the adapter was not under pressure (last 60 samples). Browsers and the compositor (dwm.exe) always keep some shared memory; the baseline stops them from being flagged.
  2. Excess = current shared usage − baseline.
  3. Enter SPILLING when for k = 2 samples in a row: load ≥ θhi and excess > Δ and shared usage is still rising (5-sample slope window). Emit SPILL_START.
  4. Leave after 3 clear samples (load < θlo or excess ≤ Δ/2). Emit SPILL_END with the duration.

The analyzer is pure and deterministic: feeding it a recorded trace gives exactly the same events as live, which is how it is unit-tested and how thresholds were tuned.

The process whose dedicated VRAM grew most in the 30 seconds before the spill started. 11.7 Banker's algorithm as GPU admission control

Before launching a new model, SpillGuard asks the Banker's question with VRAM (and commit) as the resources: Allocation = each running process's measured VRAM; Max = its observed peak × 1.1; the new launch has Max = its estimated need; Available = physical VRAM − 256 MB margin − total allocation.

Important twist: real applications are long-lived — a game or a browser never "finishes" and returns its memory, which the textbook algorithm assumes. So SpillGuard computes two verdicts and shows both in the Deadlock Lab: the classic safe-sequence result and the long-lived result, which reserves every running process's remaining need up front. Verdicts: SAFE, FIXABLE (it searches context length, KV-cache type, flash attention and GPU layers for the best configuration that fits) or UNSAFE with a plain reason ("needs 6.5 GB VRAM, 5.4 GB free; chrome.exe holds 1.4 GB"). spillguard run -- <command> can rewrite llama.cpp flags (-c -ngl -fa -ctk -ctv) or derive an Ollama model with num_ctx/num_gpu, and always asks before starting.

11.8 Security model

  • Binds to 127.0.0.1 only (loopback) — not reachable from the network.
  • A random session token per run is required for /ws and /api/*. It travels in the URL fragment (#sg=…), which browsers never send to servers, and the page removes it from the address bar.
  • Host and Origin headers are checked, blocking other websites and DNS rebinding (an attack where a malicious domain is re-pointed to 127.0.0.1). Verified: no token → 401, foreign Origin → 403, rebinding Host → 403.
  • The HTTP API is read-only. Launching programs is CLI-only behind a confirmation. Driver settings are never changed automatically.

13. SpillGuard Repro: the research experiment

13.1 Research question

Title of the research direction: "SpillGuard Repro: Reproducing and Minimizing Cross-Process GPU-Memory Performance Failures on Windows." The questions: (RQ1) can a severe slowdown of a real application, caused by another process's GPU memory use, be reproduced repeatably and recover when the pressure is removed? (RQ2) can the pressure be reduced to a minimal cause? (RQ3) which remedy fixes it with the least disruption? A failure caused by a neighbour process is called a cross-process failure; the neighbour is the co-tenant.

13.2 The matched block (baseline → pressure → recovery)

Why this design: comparing the same work, on the same machine, minutes apart, with only one thing changed is a controlled experiment. The recovery stage proves the slowdown was caused by the pressure (it goes away when the pressure goes away) and not by heat, a background update, or a broken run. All three stages contain an empty helper CUDA context, so the extra context itself is not the difference.

13.3 The recipe (experiment specification)

Every experiment is a JSON recipe validated before running (unknown keys, non-finite numbers, duplicate IDs and out-of-bound sizes are rejected).

13.4 Verdict rules (the classifier in evidence.py)

Each trial gets exactly one of three verdicts:

  • FAIL = slowdown reproduced: pressure ÷ baseline ≥ 2.0 and recovery ÷ baseline ≤ 1.25.
  • PASS = valid non-reproduction: a clean trial whose slowdown stayed below 2.0.
  • INCONCLUSIVE = anything doubtful, never silently counted as PASS or FAIL. Including: a stage failed or timed out; the requested work, prompt, model identity, realized context or generated output changed; host-memory guard tripped; Ollama reported partial CPU offload (that would be type A, not a cross-process spill); the pressure was not observed during the target (fewer than 2 overlapping samples); recovery did not return to baseline.

A whole block of repeats is FAIL or PASS only if all its trials agree; mixed outcomes are INCONCLUSIVE. The 2× threshold is an operational definition chosen before the experiment, not a hardware constant. "FAIL" names the application's failure to keep its performance, not a failure of the experiment.

13.5 Safety guards

  • Abort the stage if available host RAM falls below the floor (1.5 GiB in this recipe) or commit ≥ 90 % — a trial run while the whole PC is short of RAM would measure host pressure, not GPU spill (type C). Such trials are kept and marked INCONCLUSIVE. These guards were never relaxed to get results; memory was freed by closing apps.
  • Only processes the runner itself started can be stopped; no third-party process is killed, no driver setting is changed.
  • Requested pressure is capped (default 1 GiB, max 8 GiB explicitly declared).

13.6 Evidence bundles

Each run is saved as a bundle: recipe.json, report.json, readable report.md, per-stage helper logs, observations and trace.jsonl files (replayable in AetherOS), plus a SHA-256 manifest. SHA-256 is a cryptographic hash: changing even one byte of a file changes its hash, so verify detects any modification. Invalid trials stay in the record and in the denominator — nothing is cherry-picked. The 19 files shown in AetherOS's evidence desk were copied with the hostname removed and unrelated process names replaced by "other app".

13.7 The reducer (delta debugging)

ddmin (delta debugging minimization, Zeller & Hildebrandt, 2002) shrinks a failing input by deleting parts and re-testing, keeping a deletion only if the failure still reproduces. Its result is 1-minimal: removing any single remaining part makes the failure disappear. SpillGuard Repro implements plain ddmin over pressure actions, with a test budget and a fresh final validation. It is validated on a labelled software fixture (4 actions reduced to 2). Applying a phase/residency-aware reducer to the real witness is future work (RQ2).

16. Limitations and future work

Limitations (state them honestly)

  1. The AetherOS kernel is a simulation in the browser, not a bootable OS; OPTIMAL replacement falls back to LRU; eBPF scripts are not compiled.
  2. One machine, one GPU vendor (NVIDIA), one driver, one target model; small samples (2 trials per level, 9 valid trials for the detector check).
  3. The residency/churn mechanism is a hypothesis; PIX/ETW traces are needed.
  4. The co-tenant is a synthetic CUDA process, not a real game or browser.
  5. The live detector's thresholds were perfect on the synthetic W1 ramp, so W1 does not discriminate between threshold choices; real-world negatives are needed.
  6. Windows per-process GPU counters can drift after an app is hidden/restored (a known Microsoft issue); SpillGuard cross-checks with NVML but does not yet flag disagreements.
  7. Banker's needs maximum claims; for unknown apps "peak × 1.1" is a heuristic.

Future work

  • Run the phase/residency-aware reducer on the real witness (RQ2) and compare with plain ddmin.
  • Verify the mechanism with PIX / ETW residency events; add GPU clock/temperature controls.
  • Larger samples, randomized order, a second target (another model or engine), real co-tenants, AMD/Intel GPUs.
  • Turn "pause the co-tenant" into an automatic, consent-based remedy in SpillGuard.
  • Move the AetherOS kernel into a Web Worker; package the agent as an .exe.

17. Viva questions and answers

A. About AetherOS

Is AetherOS a real operating system?
No. It is a web application that simulates an OS kernel to teach its mechanisms. It runs inside the browser on top of Windows. The scheduling, paging, deadlock and journaling algorithms are real implementations operating on simulated processes, frames and files. The GPU part (SpillGuard) reads the real hardware.
What is a tick?
The simulated kernel's unit of time: one call of Kernel.step(), every 800 ms by default. One tick = one unit of CPU time for each core.
Why is the kernel deterministic, and why does that matter?
It uses no random numbers; the same inputs always give the same schedule. This makes behaviour explainable and lets tests assert exact outputs (e.g. Round Robin gives "A A B B").
Which scheduling algorithm is the default and why?
MLFQ, because it approximates SJF without knowing burst times: new/interactive jobs stay in the high-priority short-quantum queue, CPU-bound jobs sink, and aging every 40 ticks prevents starvation.
What is the time quantum and what happens if it is too small or too large?
The maximum CPU time a process gets before preemption in Round Robin (4 ticks here; MLFQ uses 4/8/16). Too small: many context switches (overhead). Too large: RR degenerates into FCFS with poor response time.
What is starvation and how do you prevent it?
A ready process never gets the CPU because others always win (e.g. long jobs under SJF, low priority under Priority). Prevention: aging — raising the priority of waiting processes; MLFQ's periodic boost.
What is the convoy effect?
In FCFS, many short processes wait behind one long CPU-bound process, increasing average waiting time.
Difference between SJF and SRTF?
SJF picks the shortest total burst; SRTF picks the shortest remaining time and preempts if a shorter job arrives. SRTF is the preemptive version.
How do you use two cores?
Each core has its own run queue. New processes go to the shorter queue (load balancing) unless pinned by affinity. Every tick each core picks its own process; the same process cannot be on both. If one queue is empty and the other has more than one process, the idle core steals half of them from the tail (work stealing).
What is a context switch and how do you count it?
Saving one process's CPU state and loading another's. AetherOS counts one whenever a core runs a different PID than in the previous tick, and emits a SCHED_SWITCH eBPF event.
Define turnaround, waiting and response time.
Turnaround = completion − arrival. Waiting = time spent ready but not running. Response = first time on CPU − arrival.
How big is AetherOS's memory and how are pages mapped?
32 frames × 4 KB. A process of S KB needs ⌈S/4⌉ pages; free frames are taken first; if there are not enough, the missing ones are page faults and the replacement policy picks victims from other processes.
Explain the CLOCK algorithm.
Frames form a circle with a hand. Each frame has a reference bit set on access. To find a victim the hand moves: if the bit is 1 it is cleared (second chance) and the hand moves on; the first frame with bit 0 is evicted. It approximates LRU cheaply; two sweeps always find a victim.
Why doesn't OPTIMAL really work in your OS?
Optimal needs the future sequence of page references, which no online system knows. The kernel does not model a future reference string, so it falls back to LRU and the UI says so. Optimal is used as a theoretical benchmark.
What is Belady's anomaly?
With FIFO, giving a process more frames can sometimes cause more page faults. LRU and Optimal are stack algorithms and do not have it.
What is thrashing?
When processes spend more time moving pages between memory tiers than doing work, because their working sets do not fit. The GPU spill in this project is the same phenomenon one level up: VRAM is too small for the combined working sets.
What happens in your GPF demo?
A user-mode (Ring 3) process tries to access address 0x0020 inside kernel space (0x0000–0x3FFF). The memory manager checks ring and address range, traps a General Protection Fault, records a register dump (EIP, ESP, CR3, …) and blocks the process.
How do you detect a deadlock?
Build a wait-for graph (edge P → Q if P waits for a lock Q holds) and run DFS with a recursion stack; a back edge means a cycle. With single-instance mutexes a cycle means deadlock.
Difference between deadlock prevention, avoidance and detection?
Prevention makes one Coffman condition impossible (e.g. ordered lock acquisition removes circular wait). Avoidance checks each request and only grants it if the state stays safe (Banker's). Detection lets deadlocks happen, finds cycles and recovers (kill/preempt).
Is an unsafe state a deadlock?
No. Unsafe means no safe sequence is guaranteed, so a deadlock may happen; a safe state guarantees none will.
Walk through your Banker's example.
Available 3 3 2. Need = Max − Allocation. P1 (needs 1 2 2) can run → Work 5 3 2; P3 → 7 4 3; P4 → 7 4 5; P0 → 7 5 5; P2 → 10 5 7. Safe sequence P1, P3, P4, P0, P2.
What is write-ahead logging?
Recording an operation in a journal before applying it. After a crash, committed journal entries are replayed and uncommitted ones are discarded, so metadata is never left half-updated.
What does fsck do in your OS?
After the simulated power cut it scans the journal, rolls back the PENDING (torn) transaction, replays COMMITTED but not yet checkpointed ones, marks the superblock clean and remounts the disk.
What is an inode? A superblock?
An inode is the per-file metadata record (type, size, permissions, parent). The superblock is the file-system-wide record (clean/dirty, mounted, counts, block size, journal pointers).
What is eBPF?
A Linux technology that runs small verified programs at kernel hooks to count or trace events safely without changing kernel code. AetherOS simulates probes on context switches, page faults and syscalls, with hash maps and an event ring buffer.

B. GPU memory and SpillGuard

What is VRAM?
The GPU's own dedicated, very high-bandwidth memory on the graphics card — here 6 GB of GDDR6 (6002 MB reported). Measured write bandwidth to it: 163 GB/s.
What is shared GPU memory?
System RAM that Windows lets the GPU use as a second tier, up to half of RAM (7827 MB here). The GPU reaches it across PCIe, measured at 13.2 GB/s — 12.4× slower than VRAM.
What is a spill?
When GPU data that should be in VRAM is placed in shared system memory because VRAM is full. Programs keep running but slow down, without any error message.
Who moves the data — the app, the driver or Windows?
On Windows, the video memory manager VidMm (part of the WDDM graphics kernel) manages residency, and the NVIDIA driver's sysmem fallback lets CUDA allocations succeed in system memory instead of failing. The application is not told.
Why can't the program just ask CUDA how much memory is free?
We measured it: cuMemGetInfo reported 0 MB free from 5376 MB onward while allocations kept succeeding in system memory. CUDA gives no spill signal, so an external observer is needed.
Where do your numbers come from?
Windows PDH performance counters ("GPU Process Memory" Dedicated and Shared Usage per process; "GPU Adapter Memory" per adapter), DXGI for physical VRAM and budget, NVML as a cross-check, psutil for RAM/commit, and Ollama's /api/ps for model placement. No admin rights are needed.
Why compare against physical VRAM instead of the DXGI budget?
We observed that under pressure the driver fills VRAM up to 5954 of 6002 MB, far past the 5234 MB budget; and the budget is per calling process. Physical capacity is the real limit.
Explain your detector's thresholds.
The adapter must be at ≥ 92 % of VRAM, the process's shared usage must exceed its own unpressured baseline by > 128 MB and still be rising, for 2 consecutive 1-second samples. It ends after 3 clear samples (below 85 % or excess ≤ 64 MB). Hysteresis prevents flicker; the baseline prevents false alarms on browsers that always use shared memory. In the pilot, spill raised shared usage 74 → 266 MB in the first second, so 128 MB with k = 2 detects within about 2 s.
How accurate is the detector?
On synthetic spill runs: recall 3/3, zero false positives, 0.95 s latency. But on the research trials it flagged 3 harmless cases (precision 4/7) — because counters look identical for harmful and harmless pressure. That limitation motivated the intervention-based approach.
How did you get ground truth for the detector?
Independently of the counters: the stress tool measures the write bandwidth of every 256 MB block after warming the GPU; blocks in system memory are about 12× slower, which marks the true onset.
How does Banker's algorithm relate to GPUs?
VRAM is the resource. Running processes have Allocation = measured VRAM and Max = peak × 1.1; a new model launch has Max = its estimated need. If no safe state exists, launching it would push someone into spill. Because real apps never "finish", SpillGuard also computes a long-lived variant that reserves their remaining need.
How do you estimate how much VRAM a model needs?
M = weights on GPU + KV cache + buffers + overhead, read from the GGUF file header and calibrated on this laptop (overhead 235 MB, +6.1 MB per 1 k context). Error 46 MB on average, versus 902 MB for Ollama's own estimate.
Is the agent secure?
It listens only on 127.0.0.1, needs a per-session token sent in the URL fragment, checks Host and Origin against DNS rebinding and other sites, and its API is read-only. It never launches programs from the browser and never changes driver settings.
How much overhead does SpillGuard add?
About 2.3 % of one CPU core (≈ 0.14 % of the 16-thread CPU) and 52 MB of RAM at one sample per second.

C. About the research

What exactly did you prove?
That on this laptop, a real local LLM (Qwen2.5-3B in Ollama) decodes about 2.35× slower when a co-tenant process pushes total GPU memory demand 256 MiB past physical VRAM; that it reproduced in 6 of 6 matched trials in two independent runs and fully recovered when the pressure was removed; that the slowdown is a cliff at capacity; and that pausing the co-tenant's activity fixes it while keeping its memory.
Why baseline, pressure and recovery?
It is a matched controlled experiment: the same work measured with and without the single change. Recovery confirms causation — if performance returns when pressure is removed, the slowdown was due to the pressure, not heat, background updates or a broken run.
Why is the threshold 2×?
It was declared before running, as an operational definition of "severe". It is not a hardware constant. Our results are far from the boundary on both sides (≤ 1.22× vs ≥ 2.28×), so the conclusion does not depend on the exact choice.
Couldn't the slowdown just be the co-tenant using memory bandwidth?
The −512 MiB control has the same kind of active co-tenant rewriting ~2.9 GiB every 250 ms, but everything fits: only 1.16×. And the idle co-tenant at +256 MiB holding the same bytes gave 1.03×. Only the combination over-capacity + active produces 2.3×.
Why is the output required to be identical?
To prove the work was the same. With temperature 0 and a fixed seed the model produces the same tokens; if the output changed, the trial would measure different work and is marked INCONCLUSIVE.
What does INCONCLUSIVE mean? Did you delete those trials?
It means the trial could not answer the question validly (e.g. host RAM guard tripped, model partly offloaded to CPU, pressure not observed, output changed). They are never deleted: they stay in the bundle and the denominator, and are reported.
Why did some trials stop with the commit guard?
The laptop has 16 GB of RAM and the co-tenant plus the model plus the browser pushed Windows' commit charge to 90 %. A trial under host-RAM pressure would mix a different cause (type C) into the result, so the runner stops and marks it INCONCLUSIVE. The guard was never relaxed; memory was freed by closing apps.
Why is the slowdown about 2.35× and not 12× like the bandwidth test?
The bandwidth test measured blocks that were completely in system memory. In the LLM case only a part of the working data is affected and the GPU still does most of its work from VRAM, so the end-to-end per-token time rises less than the raw bandwidth ratio.
Why does +512 MiB not make it worse than +256 MiB?
Observed, not yet explained — a plateau. A plausible explanation is that once over capacity, the manager settles into the same pattern of moving data regardless of the exact excess; verifying it needs residency tracing (future work).
Is two trials per level enough?
For a pilot, it shows repeatability (6/6 FAIL trials across two runs, all very consistent: 2.28–2.38×), but not statistical significance. Larger samples are listed as future work.
What is a SHA-256 manifest for?
It stores the hash of every file in a bundle, so any later change to the data is detected by verify. It proves integrity, not scientific correctness.
What is ddmin and 1-minimal?
Delta debugging minimization repeatedly deletes parts of a failing input and keeps deletions that still fail. 1-minimal means removing any single remaining part makes the failure disappear. It is implemented and tested on a fixture; applying it to the real witness is next.
What is new compared to existing tools?
Existing tools (Task Manager, nvidia-smi, other spill trackers) show counters. This project (1) detects spill per process with a baseline and culprit, (2) shows with a measured example that counters cannot separate harmful from harmless pressure, and (3) diagnoses by controlled intervention with matched, recovered, tamper-evident trials and compares remedies.
What would you do next?
Run the reducer on the real witness, verify the mechanism with ETW/PIX residency events, add more trials, a second model or engine, real co-tenants and other GPUs, and make "pause the co-tenant" an automatic, consent-based remedy.

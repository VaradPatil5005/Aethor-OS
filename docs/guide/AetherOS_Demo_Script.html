STEP 5 — Open the Task Manager
CLICK
Desktop icon Dash's Journal. Then the yellow button at the window's top-right to maximize.
SEE
Title "Task Manager - Dual-Core SMP Scheduler". Top bar: Pause Clock, "Tick: #…", "Policy: MLFQ (Multi-Level Feedback)", Speed slider. SAY
"This is the scheduler on two simulated CPU cores. The table at the bottom is the Process Control Block: for each process its PID, state, core affinity, the last core it ran on, remaining burst over total burst, waiting time, and its MLFQ queue level. At boot four system processes were created — kernel_daemon, window_manager, audio_server, network_sync — and you can see they are already TERMINATED because they finished their CPU bursts. The timelines are Gantt charts of the last 30 ticks, one row per core; grey means idle."
IF ASKED
"What is a PCB?" — "The record the OS keeps per process: ID, state, priority, CPU-time used and remaining, memory frames, locks held and so on."
STEP 6 — Set up a Round Robin experiment
CLICK
1. Pause Clock (it changes to "Resume Clock").
2. Policy dropdown → Round Robin (Preemptive).
3. In Spawn Process: click the name box, delete the text, type A. Click the Burst box, type 8. Click + Dispatch Process.
4. Name box → type B → + Dispatch Process. Name box → C → + Dispatch Process.
TIP
After each dispatch the name box changes to something like "task_716" — type the new name every time. Burst stays 8. Burst can be at most 50.
SAY
"I paused the clock and created three processes A, B and C, each needing 8 ticks of CPU. In Round Robin each process gets a time quantum of 4 ticks, then goes to the back of the queue. New processes are placed on the core with the shorter run queue — that is load balancing."
STEP 7 — Run it and read the Gantt chart
CLICK
Resume Clock. Wait about 15–20 seconds, pointing at the two timelines.
SEE
(Real result from my test, PIDs will differ:) CPU 0: A's PID four times, then C's PID four times, then A again. CPU 1: B runs alone. When B finishes, CPU 1's STOLEN becomes +1 and C's PID appears on CPU 1.
SAY
"Look at Core 0: A ran exactly 4 ticks — its quantum — then it was preempted and C ran for 4 ticks, then A came back. That is Round Robin. B was alone on Core 1. And when Core 1 became empty it stole work from Core 0's queue: the STOLEN counter became plus one. That is work stealing — an idle core takes half of the other core's waiting tasks from the tail of its queue, which is how real multi-core schedulers keep all cores busy."
IF ASKED
"What if the quantum is very large?" — "Round Robin becomes FCFS; too small and we waste time on context switches."  "How do you count context switches?" — "Every tick where a core runs a different PID than in the previous tick."  "What is affinity?" — "Pinning a process to one core. In the PCB table I can click the AFFINITY cell to toggle it, or choose Core 0 Only / Core 1 Only when spawning."
STEP 8 — MLFQ (the default algorithm)
CLICK
Policy → MLFQ (Multi-Level Feedback). Name longjob, Burst 50, + Dispatch Process. Scroll the PCB table down to the new row and watch its LEVEL column for ~20 seconds.
SEE
LEVEL goes Q0 → Q1 → Q2 as the job keeps using its full time slice.
SAY
"MLFQ has three queues with quanta 4, 8 and 16 ticks. A new job starts in Q0, the highest priority. If it uses its whole quantum, it is CPU-bound, so it is demoted to Q1, then Q2. Short interactive jobs stay on top. To prevent starvation, every 40 ticks all jobs are boosted back to Q0 — that is aging. MLFQ approximates Shortest-Job-First without knowing burst times in advance."
IF ASKED
"Other algorithms?" — "FCFS picks the earliest arrival, SJF the shortest total burst, SRTF the shortest remaining time, Priority the smallest priority number. All six are in this dropdown and in the Kernel menu."

Part 3 — Memory: paging and page replacement

STEP 9 — Fill the memory (still in Task Manager)
CLICK
Pause Clock. Burst box → 50. Click + Dispatch Process 9 times (any names are fine). Then Resume Clock. Close the Task Manager with the red button.
SAY
"Each process I create needs 16 KB, which is 4 pages of 4 KB. The machine has only 32 frames, so 8 processes fill the memory and the 9th must cause page faults."
STEP 10 — Open the Memory Map
CLICK
Menu bar Diagnostic → Virtual Memory Map. Maximize (yellow).
SEE
"Virtual Memory & Paging Unit", Eviction Policy dropdown (LRU), four boxes: Total Physical RAM 128 KB (32 Frames), Allocated Frames 32 Used / 0 Free, Memory Load 100%, Total Page Faults (a number above 0 — I got 6). Below: a 4×8 grid of frames F0–F31, coloured by owner process with its PID.
SAY
"This is the physical frame map — 32 frames of 4 KB. Every colour is one process. Memory is now 100% full, so when the last process arrived there was no free frame: those were page faults, and the replacement policy chose victim frames from other processes. The policy is LRU, Least Recently Used: it evicts the frame whose last access is oldest."
STEP 11 — Inspect a frame
CLICK
Click frame F0.
SEE
"Frame #0 Inspector — Status: Allocated, Owning PID: …, Virtual Page: 0, Last Access Tick: #…"
SAY
"Each frame records which process and which virtual page it holds, and the last tick it was accessed. Every tick a process runs, its frames are touched — that timestamp is what LRU uses, and the reference bit is what CLOCK uses."
STEP 12 — Change the policy
CLICK
Eviction Policy dropdown → show the four options: LRU, FIFO, Clock (Second Chance), Optimal (needs future refs: runs LRU). Choose Clock (Second Chance).
SAY
"FIFO evicts the page loaded first; it can suffer Belady's anomaly. CLOCK is what real operating systems use: a hand sweeps the frames in a circle; if a frame's reference bit is 1 it gets a second chance — the bit is cleared — and if it is 0 it is evicted. Optimal would evict the page used farthest in the future, but no real system knows the future, so I label it honestly: it falls back to LRU."
TIP
The new policy applies to the next eviction. To show it, open Task Manager and dispatch one more process, then come back — Total Page Faults increases by 4.
STEP 13 — The real-GPU "twin view"
CLICK
Scroll down inside the Memory Map.
SEE
"Twin view · real GPU memory (live)": a bar "VRAM = physical frames · 5.86 GB on NVIDIA GeForce RTX 3050 6GB Laptop GPU" and below it "Shared system RAM = backing store · spilled pages live here", then per-process bars.
SAY
"This is the bridge to my second part. On a real GPU the same idea exists: the VRAM on the graphics card is like physical frames, and system RAM acts as the backing store. When VRAM is full, Windows moves GPU data into system RAM — exactly like paging. These bars are the real memory of this laptop's GPU right now."

Part 4 — Deadlock and Banker's algorithm

STEP 14 — Open the Deadlock Engine
CLICK
Diagnostic → Open Deadlock Engine. Maximize (yellow).
SEE
Green bar "SYSTEM HEALTHY (No Circular Wait) — All process resource allocation matrices verified acyclic", a red Inject Deadlock button, the Banker's table, and "Banker's algorithm on real VRAM (live)" below.
SAY
"A deadlock needs four conditions at once: mutual exclusion, hold-and-wait, no preemption and circular wait. The engine checks continuously for a circular wait."
STEP 15 — Inject a deadlock
CLICK
Inject Deadlock.
SEE
Red bar "DEADLOCK DETECTED (Tarjan SCC Cycle) — Cyclic dependency found among PIDs: [x, y]" and "PREEMPT OFFENDING CYCLE PROCESSES:" with buttons Preempt PID #x Preempt PID #y.
SAY
"I created two threads. Alpha holds the GPU mutex and waits for the disk mutex; Beta holds the disk mutex and waits for the GPU mutex. The engine builds a wait-for graph — an arrow from a process to the process holding what it waits for — and runs a depth-first search. If the search reaches a node that is still on its recursion stack, there is a cycle: deadlock. It found the cycle between these two PIDs."
IF ASKED
"It says Tarjan — is that what you implemented?" — "The detection is DFS-based cycle detection with a recursion stack (back edge = cycle). Tarjan's strongly-connected-components algorithm is also DFS-based; my implementation uses the simpler back-edge method, which is O(V+E)."  "How did you create the deadlock?" — "Edit menu → Simulate Deadlock does the same thing."
STEP 16 — Recover
CLICK
Preempt PID #x (the first one).
SEE
The bar turns green again: "SYSTEM HEALTHY (No Circular Wait)".
SAY
"Recovery by preemption: terminating one process on the cycle releases its lock, the circular wait is broken, and the other can continue."
STEP 17 — Banker's algorithm (avoidance)
CLICK
Compute Safe Sequence.
SEE
"Safe State Discovered! Safe Execution Sequence: P1 → P3 → P4 → P0 → P2".
SAY
"Detection finds a deadlock after it happens; Banker's algorithm avoids it. Each process declares its maximum need. Need equals Max minus Allocation. Available is 3, 3, 2. P1 needs 1, 2, 2, which fits, so it can finish and return what it holds — work becomes 5, 3, 2. Then P3, P4, P0 and P2 can finish. Because an order exists in which everyone finishes, the state is safe."
IF ASKED
"Is unsafe the same as deadlock?" — "No. Unsafe means a deadlock may happen; safe guarantees it cannot."
STEP 18 — Banker's on REAL GPU memory
CLICK
Scroll down to "Banker's algorithm on real VRAM (live)". Drag the slider "Run Safety Check for a new launch claiming … GB" to the right, to about 5.5 GB.
SEE
A table of real processes with Allocation / Max / Need in MB, "NEW LAUNCH" at the bottom, and two boxes: Textbook Banker's: SAFE and Long-lived processes (SpillGuard): DENY — e.g. "needs 5.5 GB VRAM, 4.1 GB free; pythonw.exe holds 1.2 GB".
SAY
"Here I use the same Banker's code on the real VRAM of this laptop. Allocation is what each real process holds now, Max is its peak times 1.1, and the new program — say an AI model — claims 5.5 GB. The textbook algorithm says SAFE because it assumes every process eventually finishes and returns its memory. But real apps like a browser or a game never finish, so SpillGuard reserves their remaining need and says DENY — launching this would push memory into overflow. That disagreement is one of my findings: textbook Banker's is too optimistic for long-running programs."
TIP
Process names depend on what is running on the laptop. Move the slider left to about 3 GB to show both boxes say SAFE / ADMIT. Close the Deadlock window (red) when done.

Part 8 — SpillGuard live: the real GPU

STEP 29 — Explain the problem first (no click)
SAY
"Now the real part. A GPU has its own fast memory, VRAM — this laptop has 6 GB. If programs together need more than that, Windows and the NVIDIA driver don't show an error; they silently put the extra data in normal system RAM, reached over the PCIe bus. I measured that VRAM gives about 163 GB per second but data in system RAM only 13 GB per second — about 12 times slower. The program just becomes slow and nobody knows why. This is called a spill. Even CUDA's own 'how much is free' function said 0 MB free while allocations kept succeeding, so programs cannot see it. SpillGuard detects it from outside."
STEP 30 — Open SpillGuard
CLICK
Desktop icon SpillGuard. Maximize (yellow).
SEE
Header: "NVIDIA GeForce RTX 3050 6GB Laptop GPU · driver 581.83", buttons Simulated Live Replay, and a green "● agent 127.0.0.1:8765". Green banner "No heuristic alert · …% of VRAM in use". Three gauges: Dedicated VRAM (with OS budget and 92 % marks), Shared GPU memory (cap = ½ RAM), RAM commit. A "Last … s" chart. "Per-process memory tiers". "Admission check (Banker's)". "Events". Then the evidence desk further down.
SAY
"This is live data from the Python agent running on this laptop. Once per second it reads Windows' own GPU performance counters — the same ones Task Manager uses — for every process: how much is in VRAM (blue) and how much is in shared system memory (red if it is a spill). The first gauge is VRAM with two marks: the budget Windows suggests and my 92 % alarm level. The second is shared GPU memory, whose limit is half of RAM. The third is RAM commit — if the whole computer runs out of RAM that is a different problem, which I label type C."
IF ASKED
"Where do the numbers come from?" — "Windows PDH counters 'GPU Process Memory — Dedicated and Shared Usage', DXGI for the physical VRAM size, NVIDIA's NVML as a cross-check, psutil for RAM, and Ollama's API for AI models. No admin rights needed."
STEP 31 — Will this AI model fit? (Banker's admission)
CLICK
In "Admission check (Banker's)": model qwen2.5:3b-instruct, ctx 8192, f16 → Will it fit? (takes a few seconds).
SEE
"weights 1.79 GB · KV 288 MB · buffers 346 MB · CUDA 235 MB = 2.64 GB" and a verdict (SAFE / UNSAFE with a reason).
SAY
"Before launching an AI model SpillGuard predicts its GPU memory: weights, plus the KV cache — the memory that stores past tokens, which grows with context length — plus buffers and the CUDA context. I calibrated this on this laptop; the average error was 46 MB, while Ollama's own estimate was off by about 900 MB. Then it runs Banker's safety check with VRAM and RAM as the resources."
TIP
If it says "UNSAFE — needs … commit, … free", that is about RAM, not VRAM: say "it refuses because this laptop's system RAM is nearly full right now — exactly the type C protection." Try q4_0 or a smaller ctx to show the estimate shrink.

Part 10 — Research results (evidence desk)

STEP 34 — Set the research question (no click)
SAY
"Detecting a spill is not enough — I wanted to prove how much it actually hurts a real application and what fixes it. So I ran controlled experiments with a real local AI model, Qwen 2.5 3B in Ollama. Each trial has three stages: baseline — the model alone; pressure — the same work with a second program, the co-tenant, holding GPU memory; and recovery — alone again. Same prompt, same 128 tokens, temperature zero, so the output must be identical. A trial counts as FAIL — the application failed to keep its speed — only if it becomes at least 2 times slower and recovers afterwards. Anything doubtful is INCONCLUSIVE, never hidden."
STEP 35 — Open the headline chart
CLICK
Scroll down inside SpillGuard to "SpillGuard Repro · evidence desk". The headline "Dose-response + intervention + remedies (all in one)" is already open. Scroll to the chart.
SEE
Four boxes "1 Reproduce · 2 Witness · 3 Intervene · 4 Compare"; a chart of slowdown vs "planned overflow beyond physical VRAM (MiB)" with a "VRAM full" line and a "2× failure threshold" line; red dots at +256 and +512, black dots at −512 and 0; a square for the idle co-tenant.
SAY
"I varied how far the total memory demand goes past the 6 GB. At minus 512 MB — everything fits — it's only 1.16 times slower. Exactly at capacity, 1.21. But just 256 MB over capacity, decoding becomes 2.36 times slower — from 14 to 33 milliseconds per token. At 512 over it's the same, 2.33. So it is a cliff, not a slope: the moment you cross VRAM capacity, performance falls off."
STEP 36 — Every trial is shown
CLICK
Scroll to the table "Every trial (invalid ones included)".
SAY
"Every trial is listed, with baseline, pressure and recovery times. All failures recovered fully when the pressure was removed. Even the inconclusive ones are kept — two idle trials were stopped by my safety guard because the laptop's RAM commit reached 90 %."
